# ADR-001 · Persistencia y garantías del tablero

- Equipo / integrantes: ARSW-EQP-07 · Jhonatan Madero, Jhonatan Peña, Juan Murcia
- Estado: aceptado
- Fecha y commit: 2026-10-31 · base `c759ee9` · código `ca63841` · evidencias y capturas `5193639` (entrega: HEAD de `main`)

## Contexto

Un tablero colaborativo tiene dos usuarios ficticios (`ana`, `luis`) que leen y editan el mismo documento. Las operaciones son:

- **Editar el tablero** (PUT): el camino crítico. No puede perder ediciones concurrentes ni aceptar escrituras de un usuario revocado.
- **Consultar permiso para la interfaz**: decide si se muestra el botón de editar. Tolera datos de hasta 60 s.
- **Heartbeat de presencia**: dato efímero y aproximado; caduca a los 20 s.
- **Gestionar membresías** (conceder/revocar): requiere integridad referencial.

Restricciones de la práctica: instancias únicas (sin réplicas ni consenso), dos servicios que **no comparten transacción** (Gestión sobre PostgreSQL; Contenido sobre MongoDB y Redis) y Redis sin persistencia. Detener Redis es una falla de dependencia, no una partición de red.

## Decisión

1. **Motores**: PostgreSQL para membresías (fuente de autoridad), MongoDB para el contenido con preferencias embebidas, Redis solo para presencia y caché de permisos (ver `MATRIZ.md`).
2. **Frontera de atomicidad**: un documento de MongoDB. La edición usa control optimista en una sola operación:
   ```python
   collection.find_one_and_update(
       {'_id': board_id, 'version': expected_version},
       {'$set': {'title': title}, '$inc': {'version': 1}},
       return_document=ReturnDocument.AFTER)
   ```
   Si otra edición ya incrementó la versión, el filtro no coincide, se retorna `None` y la API responde **409**. Se descartó `find` + `update` porque entre ambos pasos otro cliente puede escribir (carrera lectura-modificación-escritura).
3. **Política de caché**: la caché de permisos (TTL 60 s) se usa **solo para la interfaz**. Toda escritura consulta a la autoridad (`authoritative_permission` → Gestión → PostgreSQL). Acortar el TTL u ocultar el botón no basta: reducen la ventana, pero no eliminan que un permiso revocado siga concedido en caché.
4. **Garantía de escritura**: una escritura que **comienza después** de confirmada una revocación recibe **403**. Si la autoridad no responde, la escritura recibe **503** y no se guarda, aunque exista un permiso en caché (*fail closed*).
5. **Degradación**: la presencia usa `SET key online EX ttl`, con valor y expiración en una sola escritura, y cada heartbeat renueva el TTL. Si Redis lanza `RedisError`, `touch_presence` devuelve `False`: la API responde 200 con `available:false` y aumenta `lab_degraded_total{feature="presence"}`. Solo se captura `RedisError`, no cualquier excepción, para no ocultar errores de programación.

## Alternativa considerada

**PostgreSQL con JSONB para el contenido (un solo motor transaccional).**

- Mismo control optimista: `UPDATE boards SET doc = $1, version = version + 1 WHERE id = $2 AND version = $3`.
- Ventaja principal: validar la membresía y escribir el contenido podrían ocurrir en **la misma transacción**, con `SELECT … FOR SHARE` sobre la membresía. Esto cerraría la ventana de revocación concurrente.
- **Por qué se descartó en esta práctica**: obliga a que Contenido y Gestión compartan base de datos (o a fusionar los servicios), lo que acopla su despliegue, esquema y escalamiento. Para el alcance de la clase, la garantía "revocación confirmada antes de iniciar la escritura" es suficiente y se puede comprobar.

**Alternativa también evaluada: eliminar Redis.** Sería posible: la caché se reemplaza por consultas directas a Gestión y la presencia por una tabla con `expires_at` y limpieza periódica. Se descartó porque el TTL nativo de Redis resuelve la presencia en una sola escritura sin cargar con escrituras frecuentes a las bases durables, y su caída ya está contenida por la degradación.

## Consecuencias

**Costos**
- Cada edición agrega una llamada HTTP a Gestión (latencia extra y dependencia síncrona). La caché ya no ahorra nada en el camino de escritura.
- El cliente debe manejar el 409: recargar la versión actual y reintentar o fusionar. El contador de conflictos sube, pero eso significa que **se evitó** una pérdida silenciosa.

**Fallas toleradas**
- Redis caído: las ediciones siguen con 200 y la presencia responde 200 con `available:false` (verificado en `redis-down`).
- Caché vacía o expirada: la interfaz consulta a Gestión (miss) sin efecto en la corrección.

**Fallas que bloquean (de forma deliberada)**
- Gestión/PostgreSQL caído: las ediciones responden 503 (verificado en `authority-down`). Se prefiere no estar disponible antes que autorizar con datos viejos.
- MongoDB caído: lecturas y ediciones responden 503, porque es la fuente del contenido.

**Ventana entre validar permisos y escribir (límite conocido)**
La autorización (Gestión) y la escritura (MongoDB) ocurren en servicios distintos y sin transacción compartida. Si la revocación se confirma **después** de que Contenido validó el permiso y **antes** de que MongoDB aplique la escritura, esa escritura se guarda. La ventana dura lo que una llamada HTTP más un `findOneAndUpdate` (milisegundos), pero existe. Alternativas para cerrarla:
- Frontera transaccional común (alternativa JSONB anterior).
- **Token de autorización con versión de membresía**: Gestión incrementa un `membership_version` en cada revocación; Contenido guarda ese valor en el documento y la escritura condiciona `membership_version >= v`. Requiere propagar eventos de revocación.
- Auditoría y compensación: registrar la escritura con la versión de permiso usada y revertir las que caigan dentro de la ventana.

## Historial creciente

- **Almacenamiento**: colección separada `board_history` con documentos `{_id, board_id, version, title, user, ts}`, uno por edición aceptada. Se inserta después de una edición exitosa (o con *outbox* si se exige que no se pierda ninguno).
- **Índice**: `{board_id: 1, ts: -1, _id: -1}`.
- **Consulta y paginación por cursor**:
  ```js
  db.board_history.find({board_id: "board-1", $or: [{ts: {$lt: lastTs}}, {ts: lastTs, _id: {$lt: lastId}}]})
    .sort({ts: -1, _id: -1}).limit(20)
  ```
  Se descartó `skip/limit`, porque su costo crece con la página y da resultados inestables si llegan entradas nuevas mientras se pagina.
- **Retención**: índice TTL sobre `ts` (por ejemplo, 90 días) o archivado a almacenamiento frío.
- **Por qué no embeberlo**: un arreglo sin límite dentro del tablero crece hacia el máximo de 16 MB por documento. Además, cada lectura del tablero (incluido el GET público y la carga k6) transferiría todo el historial, y cada edición reescribiría un documento cada vez mayor. Eso aumenta la latencia y la probabilidad de conflictos.

**Lo que las pruebas NO demuestran:**
- No prueban la ventana de revocación concurrente descrita arriba: los escenarios revocan **antes** de iniciar la escritura.
- No demuestran replicación, consenso ni comportamiento ante particiones (CAP): son instancias únicas.
- La carga k6 es solo de lectura y en una sola máquina: no demuestra la latencia ni la tasa de conflictos con escrituras concurrentes a escala.
- No existe medición de k6 con el código base; solo se reporta la de la solución.

## Reproducción

Requisitos: Docker Desktop en ejecución y Docker Compose v2. En Windows se usó Git Bash.

**Ajustes de Windows:**
- Si el puerto 8080 está reservado (`bind: forbidden by its access permissions`), crear un `.env` con `WEB_PORT=18080` y usar http://localhost:18080. Las herramientas internas no cambian.
- En Git Bash, anteponer `MSYS_NO_PATHCONV=1` a los comandos que reciben rutas del contenedor (por ejemplo, `/lab/evidence.sql`).

**1. Arranque**
```sh
git clone https://github.com/jhonatanmadero/Lab-8---Persistencia-consistencia-y-observabilidad.git
cd Lab-8---Persistencia-consistencia-y-observabilidad
docker compose up -d --build --wait --wait-timeout 300
docker compose run --rm tools smoke
```

**2. Restricciones SQL**
```sh
MSYS_NO_PATHCONV=1 docker compose exec -T postgres psql -U lab -d boards -e -f /lab/evidence.sql
```

**3. Baseline (código original, antes de las correcciones)**
```sh
git checkout c759ee9 -- services/content/decisions.py   # versión original del profesor
docker compose restart content
docker compose run --rm tools baseline                  # se esperan passed:false en 3 escenarios
git checkout HEAD -- services/content/decisions.py      # vuelve a la solución
```

**4. Solución**
```sh
docker compose restart content
docker compose run --rm tools acceptance        # todos passed:true, código 0
```

**5. Fallos controlados (en orden, siempre restaurando)**
```sh
docker compose run --rm tools reset
docker compose stop redis
docker compose run --rm tools redis-down
docker compose start redis

docker compose stop management
docker compose run --rm tools authority-down
docker compose start management
docker compose restart frontend
docker compose run --rm tools acceptance
```

**6. Observabilidad y carga**
- Importar `entrega/dashboard.json` en Grafana (http://localhost:3000, Dashboards → New → Import), o guardar una copia de "ARSW · Punto de partida" y agregar los 6 paneles de `docs/OBSERVABILIDAD.md`.
- Ejecutar `docker compose run --rm k6`, que dura unos 100 s. Renombrar `results/k6-carga-summary.json` antes de otra corrida, porque se sobrescribe.

Los resultados se guardan en `results/`, que no se versiona; los utilizados en esta entrega están copiados en `entrega/evidencias/`.
